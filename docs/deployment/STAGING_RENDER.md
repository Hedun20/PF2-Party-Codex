# PF2 Party Codex staging on Render

This staging environment is intentionally smaller than the full HED-98 alpha topology. It exists so two real users can test the current functional GM/player workflow from browsers before the complete Next.js/worker/Discord alpha deployment is ready.

## Topology

- One Render Docker web service in Frankfurt.
- Existing repository `Dockerfile` builds the current `apps/web` frontend and serves it from the Express server.
- Express API and frontend share one HTTPS origin.
- MongoDB remains the source of truth and is required at runtime.
- Email stays in explicit production outbox mode for staging; no external mail provider is simulated.
- Staging explicitly accepts that outbox mode as deployment-ready and exposes a verification URL only in the immediate response that creates a new account.
- Resend-verification and password-reset responses do not expose their secret links in production/staging.
- Billing remains disabled.

## First deploy

1. Create a MongoDB Atlas staging database/cluster or another externally reachable MongoDB instance.
2. In Render, create a new Blueprint from this repository and select `render.yaml`.
3. When Render asks for `MONGO_URI`, provide the staging MongoDB connection string. Do not commit it to Git.
4. Confirm the service is named `pf2-party-codex-staging` so its default URL is `https://pf2-party-codex-staging.onrender.com`.
5. Deploy the Blueprint.
6. Wait for `/api/health` to report `ready: true`. In this staging Blueprint, MongoDB connectivity plus the explicitly accepted outbox mode are the expected readiness dependencies.

`AUTH_SECRET` is generated by Render. The Blueprint does not contain database credentials or other secrets.

The staging-only `ALLOW_STAGING_REGISTRATION_VERIFY_URL=true` flag exists solely to make the first real browser smoke test possible without pretending that outbox mail was delivered. It returns the verification URL only in the successful response that created that new account. Do not enable this flag in a real production deployment. It does not expose resend-verification or password-reset links.

If Render assigns a different hostname, change both `PUBLIC_APP_URL` and `ALLOWED_ORIGINS` to that exact HTTPS origin and redeploy.

## Two-user smoke test

Use two separate browser profiles or two devices.

1. In the first browser profile, GM registers a new staging account. The registration result shows a one-time staging verification URL; open that URL in the same profile, then log in.
2. GM opens or creates the staging workspace/campaign and goes to Players.
3. GM creates an invitation for the second user's email. Players shows the newly generated invitation URL once; copy it and hand it to the second tester. Do not expect outbox email delivery.
4. Player opens that invitation URL in the second browser profile. If the player must register, use the exact invited email. Registration shows that new account's one-time staging verification URL; open it, then log in and continue back to the invitation.
5. Player accepts the invitation and enters the exact invited campaign.
6. Verify GM-only/hidden content is not present in player API responses, not merely hidden in the UI.
7. Verify public/revealed content appears for the player.
8. Verify another campaign does not inherit membership from the first campaign.
9. Verify both users can refresh/reopen the site without losing the expected auth/campaign context.
10. Verify resend-verification/password-recovery responses still do not reveal security links in the browser.
11. Record any failure against the relevant Linear issue with browser, route, account role, expected result, actual result, and request ID if present.

## Staging boundaries

This environment does not claim completion of HED-98. It does not yet deploy the target `apps/web-next`, worker, Discord bot, release/rollback automation, external email provider, custom domain, or full observability topology. Those remain part of the broader hosted alpha milestone.
